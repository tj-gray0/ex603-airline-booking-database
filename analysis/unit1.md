1.	Modelling justification

The first key decision choice was selecting passenger_id as the primary key in the passengers table, a system generated key. Candidate key choices included email or passenger name, but it’s possible for two passengers to have the same name. Email is also not an ideal choice if a passenger makes a booking with a different email in the future. The ON DELETE behavior for passengers would be “ON DELETE SET NULL” to avoid deleting any child rows in bookings. There may be scenarios where a passenger data has to be deleted, but retaining the bookings record will be important for forecast and demand planning, and financial reporting.

The flights table uses a system generated flight_id as the primary key. The reason for this choice is that the same flight number can occur multiple times in a given period. For example, flight AA101 flying from Boston to Dallas is a unique flight. However, this flight could occur every day at 9 AM. All other characteristics (flight code, duration) would be the same, so without a unique flight_id primary key, the system would not be able to easily identify unique flights. Flights is the producer in the domain model, and contains an activity flag, is_active. Rather than delete flights, in cases where they need to be removed, the is_active flag would be set to FALSE. This avoids cascading deletes or setting foreign key relationships to NULL in the bookings table that may be helpful in the future for decision making and reporting purposes. 

Bookings table is a key table as it contains information used by users of the application and critical records relevant for reporting purposes. The primary key for bookings is set to a system generated booking_id key, to ensure each booking is unique. Bookings uses two foreign keys: flight_id and passenger_id. The primary key ensures each booking is truly unique for cases when a passenger may make multiple of the same bookings. The foreign keys enforce referential integrity to ensure that each booking is associated with an existing passenger and an existing flight. 

The airports table domain is modeled to use a system generated airport_id as the primary key. In this table, candidate keys included the airport_name or airport_code. The reason these were not selected as the primary key is that airports can be renamed or close. The airport_id ensures that whatever happens to a given airport, the current airport is always identified by the unique airport_id primary key. The ON DELETE behavior for airports would be “ON DELETE CASCADE”. If an airport needs to be removed, the cascade behavior will remove the rows from the flight_routes table.

Flight routes is a junction table to model the many to many relationship that exists between flights and airports. In this domain model, I have many flights that are arriving/departing from many airports. To model this relationship, the domain model for the flight routes table uses flight_id as a foreign key and airport_id as a foreign key. There is also a VARCHAR element, airport_role, to determine if the flight is arriving or departing from that airport. The primary key is a composite of (flight_id, airport_id) meaning the same flight can appear in many rows (paired with many airports). 

Rules selected in the schema include using NOT NULL for passengers and flights. Given the critical nature of flights, all information defined in the schema is required to create a valid record. Primary keys are system generated keys to account for domain specific behavior where the same flight number is operating on a regular schedule, as often as multiple times per day. This same schema rule is carried over into the bookings table to use system generated primary key for bookings (ensuring unique bookings) to account for passengers making multiple bookings with otherwise the same information. Foreign keys are used to ensure referential integrity on the relationship between passengers and flights to bookings, and airports to flight routes. 


2.	Reflection

One decision a designer could reasonably have made differently is to not use a junction table of flight_routes. The flights table could instead be expanded with two foreign keys origin_airport_id and destination_airport_id so that all the flight route information sits in the row for a given flight. The junction table of flight_routes makes sense for two primary reasons. First, the junction table lets us model the many to many relationships that exist between flights and airports by allowing for many flights to be associated to many airports. Second, the junction table also decouples flights and airports. This domain modeling is helpful for instances when we need to remove an airport. We can retain the flight information in our system (with is_active set to false) while allowing for ON DELETE CASCADE behavior to remove airports and flight routes safely (cascade limited to flight_routes only). This protects the bookings table for historical records and lets the system use historical information for reporting in the future that might be needed by the airline for demand forecasting, financial reporting, or audit purposes.
